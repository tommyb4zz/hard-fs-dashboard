## Reproduced defects requiring code changes

### 1. A partial eMMC flush breaks later record indexing

**Where:** `Src/app_emmc_log.c:228`, `app_emmc_log_flush_locked`; `:415`, `app_emmc_log_append`; `:521`, `app_emmc_log_dump_csv`; `:605`, `app_emmc_log_dump_binary`.

`flush_locked` pads and writes the current block, clears staged bytes, then advances to the next block. Export determines record location solely as `record_index / records_per_block` and `(record_index % records_per_block) * record_size` (`:559–560` and `:655–656`). That assumes every preceding data block is full. The public flush command and both dumps can create a partial block.

**Reproduction:** the host ABI gives a 40-byte stored record and 12 records per block. Append timestamp 11, flush, append timestamp 22, flush, then binary dump. Both appends and flushes return success. The dump advertises two records but exports timestamps `[11, 4294967295]`; the second is padding with `stored_crc_valid=false`. Timestamp 22 is stored in the next fake eMMC block and is omitted by the export. The control case with both records staged before one flush correctly exports `[11, 22]`.

**Code needed:** establish a durable layout that retains the valid record count/locations of every partial block, or continue appending to a retained partial tail instead of abandoning it. Make both exports use the same layout. Version the stored format if its interpretation changes.

**Acceptance:** append/flush/append/dump must preserve every record in order; cover 1, 11, 12, 13 and multiple partial blocks, repeated dumps followed by appends, full capacity, storage write/read failures, CRC corruption and recovery behavior.

### 2. Python stream CRC does not match the firmware stream CRC

**Where:** `Src/app_emmc_log.c:96`, `app_emmc_log_crc32_update`; `:616`, `:678–690`, stream accumulation/finalization; `dump_emmc_bin.py:219`, `:227`, `:234`, Python accumulation/finalization.

Firmware uses its unfinalized CRC accumulator, initialized to `0xFFFFFFFF`, and applies the final XOR once. Python passes the same initial value to `binascii.crc32` and also XORs the final result. The APIs therefore receive different accumulator conventions. The script's own one-shot `crc32_bytes` does match firmware header/record/footer CRCs.

**Reproduction:** production C generates the valid contiguous two-record dump above; the parser accepts its header and footer and marks both record CRCs valid. Running unchanged `dump_emmc_bin.main()` with a fake serial object raises `Stream CRC mismatch: expected 0xC654FF0C, got 0xB298157A`. `binascii.crc32` over the concatenated packed records returns `0xC654FF0C`, exactly the firmware footer value. Production C's `123456789` vector is `0xCBF43926`.

**Code needed:** use one CRC convention across languages; Python can start its `binascii.crc32` chain at zero and omit the extra final XOR. Add a C-generated fixture consumed by the real Python parser.

**Acceptance:** empty dump, one record, multiple records and differently chunked accumulation; damaged header/record/footer, truncated reads, wrong counts and a supported-version policy. Successful capture must produce the expected CSV rows.

### 3. eMMC usage percentage overflows

**Where:** `Src/app_tasks.c:179`, `app_ui_calculate_usage_percent`; `:408–410`, its eMMC caller. Configured region: `Src/app_emmc_log.c:18–20`.

The expression `used * 100U` uses 32-bit unsigned arithmetic. For the configured maximum data capacity `(262144 - 1) * 512 = 134217216` bytes, a source-extracted host probe prints `quarter=25`, `half=18`, `full=4`. Half and full should be 50 and 100 for those supplied arguments. Unsigned wrap is defined C behavior, so the sanitizer does not reject it.

**Code needed:** perform the multiply/rounding in sufficiently wide arithmetic and define clamping when `used > total`.

**Acceptance:** zero capacity, empty, quarter/half/full configured capacity, near rounding boundaries, `used > total`, and large uint32 input bounds.

## Tests still needed

The current Python inventory has simulator/bus/pipeline/function-documentation tests. The host C executable includes only the production CAN driver and its configuration. `tests/test_can_pipeline.py:45–56` transports frames through virtual endpoints, serializes received data to stdin, then runs the C replay adapter; this verifies decoder output but does not execute GUI tasks, RAM/eMMC logger, touch/LCD drivers or FreeRTOS scheduling. Root's review covers the remaining closed-loop simulator boundary.

Prioritize permanent regressions for the three reproduced defects, then a timed virtual full application test exercising freshness, all auxiliary states, UI units, logging and export concurrently. Add fake storage/UART error injection, bounded logging overflow and reset recovery according to the chosen policies. Hardware measurements of task stack high-water marks, heap, worst-case poll latency and full board peripherals are still required before a hardware-readiness claim. `Inc/FreeRTOSConfig.h:50` enables stack-overflow checks, but enabling a hook does not measure stack margins; `:66` enables the stack high-water-mark API and the reviewed application does not call it.
